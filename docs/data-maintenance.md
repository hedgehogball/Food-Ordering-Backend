# 数据维护、备份与隔离恢复

本项目提供可执行的数据库备份和恢复校验。备份覆盖 6 张业务表：桌号、堂食账单、账号、自取订单、营业设置与人工验收记录、厨房小票。不会导出 MySQL 登录账号或密码，不会删除订单或旧备份。

## 已完成的验证与人工确认边界

开发环境已在 `127.0.0.1:33308` 的独立 MySQL 测试实例中完成实际 SQL 导出和恢复，逐表比对数量，并核对代表性堂食、自取、厨房小票、营业设置及验收 JSON。恢复后的默认可选桌号为 01–24。

这证明备份/恢复脚本能处理当前结构，不代表门店生产库已完成恢复演练。手机“上线验收”中的“备份、恢复与数据维护”默认待验收，只有店主实际核对线上备份计划、完成生产备份在独立环境的恢复验证、填写证据后才可手动确认。

## 环境与连接

使用 Node.js 22.9 或更高版本，以及官方 MySQL `mysqldump`、`mysql` 客户端。Windows 默认客户端目录为 `D:\phpstudy_pro\Extensions\MySQL5.7.26\bin`；其他位置用 `MYSQL_CLIENT_BIN` 指定绝对目录。Linux 默认从 `PATH` 查找客户端。

备份连接读取项目根目录 `.env` 或进程环境中的 `MYSQL_ADDRESS`、`MYSQL_USERNAME`、`MYSQL_PASSWORD`、`MYSQL_DATABASE`。数据库名称必须明确填写。请在本机私有配置中使用维护账号，不把实际值写入 README、提交到 GitHub或填写在小程序页面。云数据库应通过已授权的网络连接访问。

```dotenv
# 以下为占位示例，必须替换为你自己的数据库连接值。
MYSQL_ADDRESS=your-private-db-host:3306
MYSQL_USERNAME=backup_account
MYSQL_PASSWORD=replace_in_private_local_config
MYSQL_DATABASE=nodejs_demo
MYSQL_CLIENT_BIN=D:\phpstudy_pro\Extensions\MySQL5.7.26\bin
```

普通备份账号需要读取这 6 张表的权限；脚本使用 InnoDB 一致性快照，不锁表、不导出触发器和全局 GTID 信息。备份期间不要运行数据库结构升级。脚本不会自动修改云数据库权限。

## 手动备份

在项目根目录执行：

```powershell
npm run db:backup
```

备份输出固定在项目的 `.artifacts/backups`，不允许另行导出到共享文件夹。Windows 文件夹权限限制为当前 Windows 用户；Linux 目录权限为 700，备份文件为 600。该目录已被 Git 忽略。

成功后生成：

- `backup-时间-随机标识.sql`：6 张表的结构和数据；包含实际业务记录，应作为私有备份保管。
- 同名 `.manifest.json`：备份 UTC 时间、文件名、大小、SHA256 校验值和表名，不包含地址、账号或密码。

密码通过权限受限的临时 MySQL 配置文件传入，不出现在命令行参数或日志中；进程结束后删除临时配置文件。失败的未完成 SQL 文件会清理，已完成的旧备份不会自动删除。备份完成后应按门店维护方案保存另一个受保护的副本；仅放在开发电脑不等于云端灾难恢复。

## 隔离恢复校验

恢复脚本仅连接 `127.0.0.1:33308`，忽略生产 `MYSQL_ADDRESS` 等配置。每次新建随机名称的 `lj_restore_test_*` 数据库，若重名会失败，不提供覆盖现有数据库或回档生产库的选项。

若本机已有专用测试 MySQL 实例在该端口运行，可直接使用。若没有，维护人员应创建全新的测试数据目录，绑定 `127.0.0.1`，监听 33308；不能用门店数据库的数据目录启动测试服务。默认测试账号为 `root`、空密码，仅用于此隔离实例；如设置了测试账号，使用 `RESTORE_TEST_USER` 和 `RESTORE_TEST_PASSWORD`，不复用生产密码。

先复制上一步成功输出的 manifest 文件名，然后执行：

```powershell
npm run db:check-restore -- --manifest ".artifacts/backups/backup-实际文件名.manifest.json"
```

校验会检查路径、表名、文件大小和 SHA256，再向全新的测试库导入 SQL，核对 6 张表均可读取并记录各表数量。恢复报告也保存在 `.artifacts/backups`，标明仅为本地隔离恢复，不会替店主填写验收通过。要验收真实业务完整性，还应在该测试库抽查桌号、已结算账单、自取记录和厨房小票，并和备份时的原始统计比对。

完整开发验证可执行：

```powershell
node tests/integration/backup-restore.js
```

此程序只在专用测试实例中新建虚构业务数据，实际执行备份和恢复，再比较行数及代表性记录；不会访问云端生产库，也不会把门店验收标记通过。

## 值守与维护操作

| 时机 | 操作 | 需要保留的证据 |
| --- | --- | --- |
| 开店前 | 值守人检查专用手机电源、网络、工作台前台和提示/震动；检查最近一次云数据库备份结果 | 值守人、设备、备份时间和成功状态 |
| 交班 | 核对未接单、制作中、已出餐未交付、待收款订单及厨房小票 | 交接双方和未完成订单清单 |
| 发布或结构升级前 | 确认最近成功备份，并在独立测试库运行恢复校验 | manifest、SHA256、恢复报告及抽查结果 |
| 关店后 | 核对实收与系统统计，检查异常订单及数据维护日志 | 统计日期、核对结果和异常处理记录 |
| 维护检查 | 核对云端自动备份的有效计划、实际成功记录、保留期限与恢复权限 | 云控制台设置与最近成功时间 |

线上备份周期和保留期限以云控制台有效配置为准。本地脚本为手动工具，不会自行创建定时任务。订单数据和备份的保留期限需由店主确认后实施；当前不进行自动删除。用户的数据查询或删除请求应由店主核实身份、评估未完成订单与必要业务记录后人工处理，不通过顾客页面直接清空数据库。

未购买打印机时，“确认小票”表示已实际抄写或登记，不代表实体打印成功；未实际收到款项不得确认收银。营业期间专用手机必须保持工作台前台，离开前台或网络异常后应回到工作台核对待处理订单。
